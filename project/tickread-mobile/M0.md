**Status:** Complete  
**Completed:** 2026-08-17

## What M0 accomplished

M0 locked the data contract between the tickread pipeline and all future clients (PWA, Capacitor shell, Unity). No UI was written. The deliverable is a validated, committed foundation that any client can build on without coordinating with the pipeline team.

Before M0, the contract existed only as prose in `shared/CONTRACT.md` and the format was implicit in `build_deck.py`. After M0:

- The format is codified as JSON Schemas.
- Five fixture questions with pre-computed expected statistics are committed and machine-verified.
- A single command validates both the fixtures and the live question bank.
- The reveal-field access rule is documented in the contract and enforced by the validator.

## How to run the validator

```bash
# from the tickread-mobile directory
python shared/validate.py

# from the project root
python project/tickread-mobile/shared/validate.py
```

The validator checks (in order):

| # | Check |
|---|---|
| 1 | All 5 fixture questions conform to `question-definition.schema.json` |
| 2 | All 5 fixture sessions conform to `session-record.schema.json` and `correct = (given == answer)` |
| 3 | Stats recomputed from sessions exactly match `fixtures/expected.json` |
| 4 | `project/tickread/code/data/manifest.json` conforms to `manifest.schema.json` |
| 5 | First question of each live shard conforms to `question-definition.schema.json` |
| 6 | No fixture question ID collides with any live bank question ID |

Exit 0 = all pass. Exit 1 = at least one failure, with details printed.

## Key decisions made in M0

**Format stays at version 1 (shard-based).**  
The DESIGN.md originally referenced `question-bank.v2.json` and `manifest.v2.json`. On review, the pipeline already produces a valid and well-structured shard format. Introducing a v2 format before any client exists would be premature. CONTRACT.md now documents the live format, and the version field in the manifest provides an upgrade path when a breaking change actually occurs.

**Reveal-field rule is in the contract, not just the design doc.**  
`future`, `answer`, `symbol`, `startTime`, and `endTime` must not be accessed before the user's `given` is recorded. This is stated in CONTRACT.md and referenced in the compatibility acceptance table. A future Unity client must satisfy the same rule to pass the M0 gate.

**Fixture IDs use the `fx` prefix.**  
This makes fixture questions visually distinct from real bank questions in logs and makes the ID-collision check in `validate.py` unambiguous.

**Stats formula is locked here, not in the client.**  
The expected stats in `fixtures/expected.json` are the authoritative answer for what hit rate and groupings mean. Any client that produces a different number for the same inputs is wrong.

## What M0 does not cover

- Any UI or browser code
- Offline caching or Service Worker
- PWA install manifest
- Session persistence across app restarts
- Cumulative statistics across multiple rounds

Those are M1 (mobile web MVP) and later.
